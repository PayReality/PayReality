# Enterprise Knowledge Architecture

**A design, not a build.** Nothing in this document is implemented; per this milestone's explicit instruction, Enterprise Knowledge is architected here, not constructed. PROPOSED throughout, grounded in this platform's own already-verified architecture (`ARCHITECTURAL_DECISION_HISTORY.md`, `ENGINEERING_PRINCIPLES.md`), not invented independently of it.

## The question this document answers

Runtime Authority evaluates whether an action matches an organization's own Runtime Policies. A real policy frequently needs to reference a prerequisite Runtime Authority cannot itself determine: is this vendor approved, is AML complete, is insurance active, is training current, is the risk level acceptable, is budget available, is a specific delegation still valid. Every one of these facts lives in a different, external, authoritative enterprise system. Enterprise Knowledge is the layer that lets a Runtime Policy reference such a fact, without making Runtime Authority itself the source of truth for it, and without breaking the one guarantee the entire platform is built around: the same policy and the same input always produce the same decision (`ENGINEERING_PRINCIPLES.md`'s "fail closed, always" and `ARCHITECTURAL_DECISION_HISTORY.md`'s "why OPA" both depend on this holding).

## Why this is architecturally hard, stated precisely

A live call to an external system, made synchronously during policy evaluation, would technically work, and would also break determinism in a way this platform has never allowed anywhere else: the same Intent, evaluated twice, could produce two different outcomes depending on network timing, external-system availability, or a value that changed between the two calls, and neither outcome would be reproducible later for an auditor. Every other input to a decision (the Intent itself, the compiled Runtime Policy, the Authority Graph) is either supplied at request time or already a versioned, point-in-time snapshot. Enterprise Knowledge has to become the same kind of input, a versioned, point-in-time snapshot, resolved before evaluation, never fetched live during it, or it introduces the one category of nondeterminism this platform has structurally avoided everywhere else.

## Options considered

| Option | What it is | Verdict |
|---|---|---|
| **Live APIs** (call the external system synchronously, inside the decision path) | The naive approach | **Rejected as the evaluation-time mechanism.** Breaks determinism and reproducibility exactly as described above, and puts a third party's uptime directly in Runtime Authority's own critical path. **Retained as a legitimate refresh mechanism**, used by a connector to periodically pull fresh data into a local store, never called synchronously during evaluation itself. |
| **Caches** (a local, periodically refreshed store of external facts) | A local read-model, refreshed out-of-band | **Adopted as the core mechanism.** A decision reads a local, versioned snapshot; latency becomes a local lookup, not a network round-trip, and the exact snapshot used can be recorded alongside the decision for reproducibility, the same discipline already applied to Runtime Policy versions. |
| **Event streams** (external systems push change events; the platform maintains an up-to-date projection) | A push-based freshness mechanism | **Adopted where a source system supports it**, as the preferred way to keep the cache above fresh rather than polling. Not adopted as the sole mechanism, since most enterprise systems this platform will integrate with in an early pilot phase won't have a usable event feed on day one; polling remains the honest fallback. |
| **Enterprise adapters** (a per-system integration module normalizing that system's data into a canonical fact shape) | The connector layer itself | **Adopted**, this is the mechanism binding a specific enterprise system (via live API polling, an event feed, or both) to the local cache. See `ENTERPRISE_DATA_CONNECTOR_STRATEGY.md` for the full design. |
| **Knowledge Graphs** (a general-purpose graph model of all enterprise facts and their relationships) | Heavy, general-purpose relationship modeling | **Rejected as the primary data model.** The actual need (a set of independently-sourced, mostly-boolean-or-scalar facts, each scoped to one subject) does not require general graph traversal, and a rich, general-purpose graph risks becoming a second, drifting source of truth exactly of the kind this design has to avoid. The existing Authority Graph already fills the one place this platform genuinely needs graph structure (delegation and reporting relationships); Enterprise Knowledge should not duplicate that model for an unrelated problem shape. |
| **Boolean assertions** (each prerequisite as a simple, named, sourced, timestamped fact) | The data model itself | **Adopted**, this is the shape every fact takes: a subject, a key, a value, a source system, a timestamp, and (see Trust Services, below) an optional cryptographic attestation. |
| **Trust services** (a source system cryptographically attests to a fact, rather than the platform trusting an unsigned API response or cache entry) | An attestation-based trust model | **Adopted as the preferred pattern where a source system can support it**, since it extends this platform's own existing Ed25519-signing discipline (already used for Agent certificates and Evidence) to external facts, rather than introducing an unrelated trust model. Where a source system cannot produce a signed attestation (the realistic majority case, at least early on), the connector's own identity and the freshness/expiry policy below serve as the trust boundary instead, honestly weaker than a full attestation but still an explicit, bounded trust decision rather than an implicit one. |
| **Policy attributes** (external facts injected into the same OPA input document Runtime Policies already evaluate against) | The integration mechanism | **Adopted.** See "How it integrates," below. |

## How Enterprise Knowledge should work

1. A **connector** (see `ENTERPRISE_DATA_CONNECTOR_STRATEGY.md`) for a specific enterprise system resolves one or more named facts (for example, `vendor.approved`, keyed to a vendor identifier) from that system, via whatever mechanism the system actually supports (an event feed, a scheduled poll, or, if the system offers it, a signed attestation).
2. Each resolved fact is written to a local **Enterprise Knowledge store**, organization-scoped exactly like every other tenant-owned table in this platform, as a boolean or scalar assertion carrying its subject, key, value, source, resolution timestamp, and an explicit expiry.
3. At Intent evaluation time, the platform resolves every Enterprise Knowledge reference a policy's conditions actually name, reading only from this local store, never calling out to a live external system in the request path, and attaches the resolved values to the OPA input document as a new, clearly namespaced section (`enterprise_knowledge`), alongside the existing `intent`, `context`, and `agent` sections `domain/decision/engine.py`'s input already assembles today.
4. OPA evaluates exactly as it does today; nothing about its own evaluation model changes. A condition referencing an Enterprise Knowledge fact is just another field reference, using the exact same `Condition`/`Operator` machinery every other Runtime Policy condition already uses.
5. The specific fact values used are recorded in the resulting Evidence record, the same way the specific policy version and bundle hash already are, so a decision remains fully reproducible: an auditor can see not just what the policy said, but exactly what external facts it was evaluated against, and when those facts were last confirmed true.

## How it remains deterministic

Because step 3 above resolves every fact from a local, versioned snapshot before evaluation, not during it, the same policy plus the same recorded fact snapshot always produces the same decision, exactly like every other input to this platform's evaluation model. Determinism is preserved by construction, not by hoping the external system behaves consistently.

## How latency stays below enterprise expectations

A decision's evaluation path never makes a new network call to an external enterprise system. The added cost of Enterprise Knowledge is a local, indexed lookup, the same order of magnitude as every other database read already in the request path (resolving the Agent's certificate, the active Runtime Policy set), not a new external dependency's round-trip time. This is the direct consequence of rejecting live APIs as the evaluation-time mechanism, not a separate optimization.

## How enterprise systems remain authoritative

The Enterprise Knowledge store is explicitly a read-only mirror, never a write path back to the source system, and never presented as more authoritative than its own source. Every fact carries an explicit expiry; a fact past its expiry is treated as unknown, not as its last-known value, triggering the platform's existing fail-closed behavior (HUMAN_REVIEW) rather than silently trusting stale data. This mirrors, deliberately, how this platform already treats an unreachable OPA instance or an unverifiable certificate: uncertainty resolves to review, never to a default ALLOW.

## What this document does not decide

The specific enterprise systems to integrate first, the specific expiry windows per fact type, and the specific UI a reviewer uses to see which Enterprise Knowledge facts a given decision relied on are all real, necessary decisions this document deliberately leaves open, since they depend on which real pilot customer's real systems this capability gets built for first, not on an assumption made before one exists.
