# Milestone 4: Azure Production Readiness and Render Retirement

**Status: audit and design complete. No production code changed. No infrastructure changed. No traffic moved. Render has not been touched.**

**Naming note, read this first.** This document uses "Milestone 4" in the sense the requesting prompt used it: the next step after the enterprise-hardening roadmap's "Milestone 3 (Enterprise Surface Isolation)," which itself followed "Milestone 2 (Multi-Tenant Foundation)." That is a different numbering track from the Azure migration's own internal program, which lives entirely under `AZURE_MIGRATION/` and already has its own Milestones 1 through 6, plus two later programs (`PRODUCTION_CUTOVER/`, `PRODUCTION_BOOTSTRAP/`) that are not numbered as milestones at all. To avoid a fourth collision on the word "Milestone," the rest of this document refers to that existing body of work as "the Azure migration program" and cites its documents by path, never by a bare number.

## Why this document exists

Prior sessions' memory described the Azure migration program as far along: staging live in `centralus`, identity-first Key Vault and Storage RBAC in place, a Key Vault soft-delete naming collision resolved. That memory was accurate as far as it went, but it predates work this session found already sitting in the repository: a full second resource group (`rg-payreality-prod-cus`), a completed "Production Bootstrap" program that actually provisioned it, and two earlier cutover attempts that each independently concluded the platform was **not ready to cut over**, for reasons that turned out to be about missing scope (no prod environment, no data-migration tooling) rather than platform quality.

This session's job was to verify all of that directly rather than trust any prior account of it, including its own memory, and to produce the audit, verification, and planning documents the requesting prompt asked for. Four research passes ran against the live repository and the live Azure subscription: a full read of every file under `AZURE_MIGRATION/` and its Terraform, a live resource inventory via the `az` CLI across every category the prompt named, a repository-wide grep for every remaining Render dependency, and a live functional verification pass (health checks, telemetry queries, DNS resolution) against both deployed Container Apps. Their findings are synthesized below, phase by phase, plus one fact this document verified directly against the repository's own git history that none of the four passes had access to: **the exact commit Azure's production Container App is currently running, and where it sits relative to the multi-tenant and Enterprise Surface Isolation work.** That fact turns out to be load-bearing for the final verdict.

## Constraints honored throughout

No change was made to Runtime Authority, Runtime Policy evaluation, OPA, or Authority Intelligence. No product functionality was added. No code from Milestones 1 through 3 was touched. Nothing was removed from Render, and no DNS record, Vercel environment variable, or Azure custom domain was changed. Phases 1 through 7 are audit, verification, design, and planning only. Phase 8, per the requesting prompt's own instruction, is real documentation editing, and is called out separately at the end of this document with an exact file list.

## Phase 2: Render Dependency Audit (document only, nothing removed)

Nine categories, all repository-wide, read-only.

**1. `render.yaml`** exists once, at the repository root. It declares one free web service (`payreality-api`, Docker runtime, Oregon region), a `healthCheckPath: /health`, and six environment variables, three of which are `sync: false` (manually pasted secrets: `DATABASE_URL`, `EVIDENCE_SIGNING_KEY_B64`, `ANTHROPIC_API_KEY`). It deliberately declares no `databases:` block, adopting an existing free Postgres instance instead of provisioning a new one on Blueprint apply.

**2. Environment variables.** The only Render-specific variable name read anywhere in application code is `RENDER_GIT_COMMIT`, read once in `server/app/main.py`'s `/version` endpoint, with a fallback of `"unknown"` outside Render. `server/app/config.py` has no Render-shaped default anywhere; its default `DATABASE_URL` is a local development value.

## Phase 4: Production Data Migration Plan (design only, not executed)

The Azure migration program's own `PRODUCTION_CUTOVER/02_DATA_MIGRATION_ASSESSMENT.md` already designed a `pg_dump`/`pg_restore` migration via Blob Storage staging, with explicit handling for two things generic migration guides miss on this platform: Evidence hash-chain continuity across the cutover boundary, and cross-registering Render's signing key (`signing_key_prod_v1`) into Azure's `signing_keys` table so historical Evidence remains verifiable afterward. That plan was written before this session's confirmation that Azure prod's application code predates Milestone 2/3's schema changes, so it needs one addition, not a redesign: every table that gained an `organization_id` column, a lifecycle status column, or a new table entirely (`organization_invitations`, the lifecycle columns on `organizations`, `policy_extraction_uploads.organization_id`) did not exist when that plan was authored, and the plan's schema-compatibility section should be re-read against the current models before this migration is ever attempted for real. This document does not re-author that plan from scratch; it restates its shape, adds this one required update, and treats it as the canonical design, per the requesting prompt's instruction not to redesign or duplicate what already exists in the repository.

**Migration order.** Application code is redeployed to prod first, and the health check and Alembic head revision are confirmed against an empty or pre-existing prod database before any data touches it, since prod's current schema (from commit `5e1c3ad`) is several migrations behind `HEAD` regardless of whether Render data ever gets involved. Only after that redeploy is verified does a `pg_dump` of Render's database (if a real one is decided to exist, see below) get taken and restored into prod's Postgres via the existing Blob Storage staging path.

**Downtime.** A brief, planned maintenance window is required for the actual cutover moment (Render's database briefly set read-only or the application briefly stopped, dump taken, restore run, application resumed against Azure), not a zero-downtime online replication approach; the existing plan already reaches this conclusion for a database this size and this is not revisited here.

**Rollback.** Identical to the DNS-level rollback in Phase 7: Vercel's `VITE_API_URL` (or the registrar's CNAME, if that path was used instead) reverts to Render, which is never stopped or modified during the window, so a rollback is a configuration change, not a data operation, provided the cutover window is short enough that no writes land in Azure's Postgres that would need reconciling back into Render's.

**Validation.** Row counts per table, foreign key and sequence integrity (`pg_dump`/`pg_restore` preserve both correctly for a same-version Postgres major-version migration, which this is, v16 to v16), and, specific to this platform, an end-to-end Evidence chain verification run against the restored data (`GET /v1/evidence/chain/verify` for every organization, using the fix Milestone 3 already shipped) and an OPA package/Runtime Policy spot-check comparing a sample of compiled bundles before and after.

**Tenant safety.** Because Milestone 2 and 3 made every relevant table organization-scoped, a migration that runs after the prod redeploy (per the ordering above) carries that scoping automatically; a migration run against prod's current, pre-multi-tenant schema would not, which is one more reason the redeploy must happen first.

**The open question this plan cannot resolve on its own, and should not guess at:** whether Render's database, today, on 2026-08-13, actually contains real data worth migrating. The Azure migration program's own "Production Bootstrap" phase treated "no real production data has ever existed" as a user-supplied business fact it explicitly could not independently verify, since no tooling available to any session in this engagement can inspect Render's database directly. That finding may still be accurate, or real usage may have accumulated since. This document does not assume either answer; it designs the mechanism to work correctly if real data does exist, and notes that the very first step of any real cutover attempt should be confirming that fact directly (a row count against Render's database, via a connection this session does not have), not inheriting the prior assumption unchecked.

## Phase 5: Deployment Pipeline Design

Today's deployment is entirely manual: build an image locally or in CI-without-deploy, push it to the relevant ACR by hand, update the Container App's revision by hand. `.github/workflows/ci.yml` builds and tests on every push but stops there; it does not push an image or trigger a deployment. This phase designs, but does not build, the pipeline that would replace that manual step.

**CI.** Extend the existing `ci.yml` (test, then build) with a build-and-push stage, gated on `main`, that pushes to the staging ACR only, tagged with the short commit SHA (matching this project's existing `staging-<sha>` / `prod-<sha>` convention). No change to the existing test job.

**CD, staging.** A new workflow, triggered on a successful push to the staging ACR, updates `ca-payreality-api-staging-cus`'s revision via `az containerapp update --image ...`, then polls `/health/ready` on the new revision before considering the deploy successful. Container Apps' own single-revision-mode behavior (already observed directly in the Azure migration program's Milestone 5 rollback drill: the old revision kept serving `/health` throughout a bad deploy) is the natural rollback mechanism for staging and needs no extra tooling.

**CD, prod: manual promotion, not automatic.** Given prod's current staleness (44 commits behind, per Phase 3) and the requirement that this is an infrastructure and operational hardening project, not a new feature, the correct design is a promotion gate, not full automation: an operator explicitly re-tags a staging image that has already run in staging for a defined soak period as `prod-<sha>` and pushes that exact tag to the prod ACR, which triggers the same update-and-health-check workflow scoped to `ca-payreality-api-prod-cus`. This is a deliberate asymmetry (staging auto-deploys, prod requires a human to promote a specific, already-tested image), matching how the two Container Apps are already configured differently (`min_replicas` 0 versus 1) rather than inventing a new deployment concept.

**Database migration ordering.** Alembic migrations run as a separate step before the Container App revision update, against the target environment's database, using the same Managed Identity the application itself uses (no new credential). This must run and succeed before the new image is promoted to serving traffic, matching this platform's existing "additive, nullable-first" migration discipline (documented repeatedly across Milestones 2 and 3): a migration that only adds nullable columns or new tables is always safe to run ahead of the code that starts using them.

**Runtime Policy deployment ordering.** No change: Runtime Policies are data, created and activated through the application's own API and lifecycle service, never through the deployment pipeline. This phase does not touch that boundary.

**Health checks, monitoring, alerting, recovery.** The existing `/health` and `/health/ready` endpoints and the five Azure Monitor alert rules per environment (Phase 1) are sufficient as the pipeline's own success signal; no new health surface is needed. A failed health check after a revision update should trigger an automatic revert to the prior revision (`az containerapp revision activate` on the last-known-good revision), which is a config change to the CD workflow, not new application code.

**Blue/Green or Canary: not recommended at this stage.** Container Apps' revision model already gives an approximation of blue/green (old revision stays up while a new one activates), and this platform's traffic volume (confirmed near-zero real usage in Phase 3) does not justify the added complexity of traffic-splitting canary rules. This should be revisited if and when Azure actually carries real production load; building it now would be scope beyond what this milestone's constraints allow ("do not build new features").

## Phase 6: Azure Operational Hardening Review

Security, networking, RBAC, and secrets are, on the whole, in strong shape: everything is Managed-Identity and RBAC-gated with no shared keys or connection strings baked into Terraform, every sensitive resource has either a Private Endpoint or (for Postgres) VNet delegation instead of a public network path, and Key Vault has both soft-delete and purge protection enabled. The findings below are specific, not a general "needs more security" note.

1. **Terraform drift risk on the AI modules (repeated from Phase 1, most important item here).** Add an explicit per-environment toggle (a boolean variable, defaulting false, set true only in `staging.tfvars`) before the AI Foundry and AI Search modules are ever applied again, so a routine `terraform apply -var-file=prod.tfvars` cannot silently create either service in prod.
2. **Storage accounts allow public network access even where a Private Endpoint exists.** All three application storage accounts (`stprstagingadzg`, `stprprodtq1k`, and the Terraform state account) have `publicNetworkAccess: Enabled`; a Private Endpoint is additive, not exclusive, so this leaves a public path open that the private one was presumably meant to replace. Recommend setting `public_network_access_enabled = false` on the two application storage accounts, matching Postgres's own posture, once confirmed nothing outside the VNet needs the public path (Terraform itself, which runs outside the VNet, is the one caller that might).
3. **Terraform state storage account allows public blob access** (`allowBlobPublicAccess: true`), the one place this project's otherwise consistent private-by-default convention was not applied. State files can contain sensitive values; recommend disabling this and adding a Private Endpoint or at minimum IP-restricting it to known CI/operator ranges.
4. **The orphaned restore-drill Postgres server** (`psql-payreality-staging-cus-restoretest`) and the **soft-deleted Key Vault** (`kv-pr-staging-adzg`, unpurgeable until 2026-11-08) are both real, standing state with no current owner or purpose. Recommend an explicit keep-or-delete decision on the Postgres server now (it has been open since the Azure migration program's Milestone 5 and never closed), and noting the Key Vault's purge date on a calendar so its eventual cleanup isn't forgotten.
5. **`ANTHROPIC_API_KEY` remains an unrotated placeholder in both environments**, confirmed via secret metadata (Phase 3). This is a functional gap (AI features cannot really work in prod without it), not strictly a security one, but it means prod's own `ai_enabled: true` status is not trustworthy today and should not be relied on until this is set to a real value.
6. **No account lockout after repeated failed logins**, and **distributed rate limiting does not exist** (the application's rate limiter is in-process memory, per `SPECIFICATION/14_SECURITY_MODEL.md` §14.5 and §14.7). Neither is new to this milestone, both are already-disclosed limitations, and neither is an Azure infrastructure gap; they are restated here only because "operational hardening" is this phase's scope and a reviewer should not need to cross-reference a different document to find them.
7. **Cost.** The `docs/COST_ASSUMPTIONS.md` file in the Azure migration program states its own estimates were never validated against live Azure pricing. This document does not re-derive cost, only notes that this stated caveat is still open and should be closed before any decision that turns on cost (e.g., whether to keep the orphaned restore-test server, item 4 above).
8. **Scaling.** Staging's `min_replicas: 0` means a cold start on the first request after idle, acceptable for a non-production environment; prod's `min_replicas: 1` avoids that. Neither environment has zone-redundant high availability. This is consistent with a pilot-to-early-production posture and does not need to change until real traffic volume or an uptime SLA makes it necessary; flagged here as a known, deliberate tradeoff, not an oversight.

## Phase 7: Render Retirement Plan

**This plan is not ready to execute, and this document does not treat it as ready.** Per the requesting prompt's own sequencing ("only after Azure is fully verified"), and per Phase 3's finding that Azure prod is running application code 44 commits stale and missing the entire Milestone 2/3 multi-tenant isolation work, retirement cannot begin until that gap is closed. The plan below is the design for when it can.

**Preconditions, all of which must be true before step 1 below is taken, none of which are true today:**
- Azure prod redeployed to a current commit (at minimum, including every fix from Milestone 2 and Milestone 3).
- The Phase 4 data migration (if Render is confirmed to hold real data worth migrating) completed and validated.
- A custom domain and certificate bound to the prod Container App, so cutover is a DNS change to a stable Azure hostname, not a temporary default hostname.
- The two live-fire-untested alert rules (Phase 1) either confirmed to work or replaced with ones that have been.
- `ANTHROPIC_API_KEY` set to a real value in prod, if AI features are meant to be live at cutover.
- An explicit decision recorded on the two orphaned resources (Phase 6, item 4).

**Cutover order, once preconditions are met:**
1. Lower the DNS TTL on whichever record currently fronts the backend (`api.aisecurewatch.com`'s CNAME, per Phase 3) to a short value (60 to 300 seconds), and wait out the old TTL, so the eventual switch propagates quickly.
2. Point that record at the prod Container App's custom domain (or update Vercel's `VITE_API_URL` directly, whichever the live routing check in Phase 3 ultimately confirms is the actual mechanism in use).
3. Watch Application Insights on Azure prod for real request volume to begin appearing, and watch Render's own metrics (if accessible) for it to drop off, as the live confirmation that traffic has actually moved, not just that DNS has propagated.
4. Run the full smoke test (`scripts/smoke_test.py`) against the new production URL.
5. Leave Render running, untouched, for an explicit observation window (the Azure migration program's existing rollback docs use this same principle; this plan does not shorten it) before touching anything on the Render side.
6. Only after that window passes with zero rollback triggered: deprovision the Render web service and its Postgres database, and, separately, remove or explicitly mark historical the Render-specific artifacts listed at the end of Phase 2 (`render.yaml`, the `RENDER_GIT_COMMIT` fallback, the SDK's default base URL if it should change, the documentation list). The `RENDER_GIT_COMMIT` fallback in `main.py` can be left in place harmlessly even after retirement, exactly as the Azure migration program's own hardening plan already noted; it does nothing on a platform that never sets that variable.

**Rollback, at any point before step 6:** revert the DNS record or Vercel variable back to Render. Because Render is never stopped, scaled down, or otherwise modified during the window, this is a pure configuration reversal with no data to reconcile, provided no writes have landed in Azure's database that would need replaying back into Render's. This exact mechanism has three independent, previously-written versions in the Azure migration program's own docs; this plan does not add a fourth, it just restates the one mechanism all three already converge on.

**Final shutdown.** Deprovisioning Render's web service and database is the only step in this entire plan that is genuinely irreversible, which is why it is the last step, gated on the explicit observation window in step 5, not on DNS propagation alone.

## Final Readiness Assessment

**Is PayReality ready to cut over from Render to Azure today? No.**

Azure's infrastructure is real, live, and largely well-built: both environments are healthy, RBAC and Managed-Identity coverage is thorough and consistent, backups are drill-tested, telemetry is flowing, and the platform-level design decisions (identity-first isolation, VNet delegation for Postgres, RBAC-only Key Vault) are sound. That much was already true before this milestone and remains true now.

What blocks cutover is not infrastructure quality, it is that **Azure prod is not currently a deployable target for a real cutover**, for three independent, each individually sufficient reasons, all confirmed live in this milestone:

1. **Application code staleness.** Prod is running commit `5e1c3ad`, 44 commits and two entire enterprise-hardening milestones behind `HEAD`, missing every multi-tenant isolation fix including the five BLOCKER-severity gaps Milestone 3 closed. Cutting over today would put a known-vulnerable build into production.
2. **No traffic path exists yet.** No custom domain, no certificate, and no Azure DNS zone exist for either Container App. There is nothing to cut DNS over to today even if the code were current.
3. **AI features are not real in prod.** No AI Foundry or AI Search resource exists there at all, and the placeholder `ANTHROPIC_API_KEY` means the application's own status endpoint is very likely misreporting `ai_enabled: true`.

None of these are new problems this milestone introduced; they are the same three-way gap the Azure migration program's own Milestone 6 and `PRODUCTION_CUTOVER/` audits already found and reported as **NOT READY**, confirmed still true today by direct, independent re-verification rather than assumed to still hold from memory.

**Recommendation for the next milestone.** Before any DNS cutover is attempted: redeploy Azure prod to current `HEAD` and re-run the full verification this milestone performed against the new deployment; decide and implement the AI-services question for prod (either provision AI Foundry/AI Search there deliberately, behind the Phase 6 Terraform toggle, or explicitly decide prod runs without AI features for now); bind a custom domain and certificate to the prod Container App; and confirm, with an actual credentialed check this session did not have, whether Render's database holds real data that needs the Phase 4 migration or can skip straight to a schema-only bootstrap as the Azure migration program's own Production Bootstrap phase already did once before. Only after those four items close does Phase 7's cutover plan become executable rather than theoretical.
