# Identity Model

**Status:** final, Milestone 2. **Principle:** Managed Identity wherever possible; secrets never live inside Terraform variables, application configuration, code, or pipelines; Key Vault owns every secret value.

## The two identities

| Identity | Module | Granted | Never granted |
|---|---|---|---|
| Runtime (`id-payreality-containerapp-*`) | `managed-identity` | `AcrPull` (registry), `Key Vault Secrets User` (read-only), `Storage Blob Data Contributor` | `AcrPush`, any Key Vault management role, any deployment/control-plane permission |
| CI/CD (`id-payreality-cicd-*`) | `managed-identity` | `AcrPush` (registry) | Key Vault access, Storage access, anything the running application itself needs |

Two identities, not one, because the application and the pipeline that deploys it must never share a permission boundary — a compromised running container should never be able to push a new image; a compromised CI run should never be able to read production secrets.

## No client secret, no certificate, anywhere

GitHub Actions authenticates to the CI/CD identity via **workload identity federation** — GitHub issues a short-lived OIDC token, Azure trusts it because of a `azurerm_federated_identity_credential` scoped to one repository and one branch. Nothing is generated, stored, rotated, or capable of leaking, because nothing long-lived exists in the first place.

## Secret lifecycle

1. **Origin.** A secret either already exists in Render's production environment today (`EVIDENCE_SIGNING_KEY_B64`, `EVIDENCE_SIGNING_KEY_ID`, `ADMIN_API_KEY`, `ANTHROPIC_API_KEY`) or is generated fresh by this Terraform project itself (the Postgres administrator password).
2. **Storage.** Every secret lives in exactly one place: Azure Key Vault. Terraform-generated secrets are written by the `postgres` module directly, since Terraform is the value's own origin. Render-originated secrets get a **placeholder** value (`PENDING-MILESTONE-5-MANUAL-ENTRY`) from the `key-vault` module now, with `lifecycle { ignore_changes = [value] }`, so a real value can be set later without any risk of a future `terraform apply` reverting it.
3. **Migration (Milestone 5, not this one).** The real value moves from Render's environment store to Key Vault via `az keyvault secret set`, run directly against the exact placeholder secret name — **never** through a Terraform variable, a `.tfvars` file, or a pipeline log. This is the one absolute rule this entire identity model exists to enforce: a secret that already exists somewhere else does not get a second, Terraform-visible copy of itself just to move house.
4. **Consumption.** The Container App resolves every secret via its runtime managed identity at container start, before the application process runs. `server/app/config.py` sees an ordinary environment variable — no application code change, no Azure SDK dependency added to the app.
5. **Rotation.** Stays a human/CI action against Key Vault directly (`Key Vault Secrets Officer` role, not held by either managed identity in this milestone) — consistent with Sprint 1's own recommendation that `ADMIN_API_KEY` specifically needs a real rotation mechanism, which is infrastructure-independent work, not something this Terraform project needs to build.

## What "secrets never live inside Terraform variables" means in practice here

No `variable` block in this entire project is typed to hold a real secret value, and no `.tfvars` file (`environments/staging.tfvars`, `environments/prod.tfvars`) contains one — confirmed directly, both files are checked into git specifically because neither has anything sensitive in it. The one exception that looks like it might violate this — the Postgres administrator password — doesn't: it is generated by `random_password` *inside* Terraform's own execution, never passed in, and Terraform's own state file (which must be treated as sensitive regardless, via the encrypted, access-controlled remote backend `AZURE_MIGRATION/bootstrap/` provisions) is the only place it's ever recorded outside Key Vault itself.
