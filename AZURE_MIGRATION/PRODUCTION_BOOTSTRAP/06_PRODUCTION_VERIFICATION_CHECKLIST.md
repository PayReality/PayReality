# Production Bootstrap Program — Phase 5: Production Verification Checklist

To be executed after `05_DEPLOYMENT_INITIALIZATION_PLAN.md`'s Step 8, before `07_DNS_CUTOVER_PLAN.md` begins. Unlike the prior program's validation plan (which found several checks permanently "Blocked" for lack of real data), most items here become genuinely executable in a fresh prod environment, because the real Organisation Owner creating the first real policy *is* production usage, not synthetic test data waiting on a migration that will never come.

## API health

**Check:** `/health` → `200`; `/health/ready` → `200` with `database: true, opa: true`.
**Pass criterion:** both true, verified live, not inferred from deployment success.

## OpenAPI surface

**Check:** `/openapi.json` matches the same schema already confirmed byte-identical to Render's in Milestone 4 (92 paths, 112 operations) — confirms prod is running the same application code, not a divergent build.
**Pass criterion:** diff against the previously-captured schema is empty, or any difference is an intentional, documented code change made since.

## OPA

**Check:** via container exec, `curl http://localhost:8181/health` → `{}`; `curl http://localhost:8181/v1/policies` reflects whatever policies exist (empty immediately after bootstrap — correct; non-empty after the smoke test's first real policy is published).
**Pass criterion:** OPA process healthy; policy bundle contents match the database's actual `runtime_policy_records` state.

## Runtime Truth / Policy evaluation

**Check:** the real Organisation Owner (claimed via `/setup-owner`) publishes one real production policy, then submits one real intent expected to match it. Confirm the recorded decision matches what OPA actually evaluated.
**Pass criterion:** the decision (ALLOW/DENY/HUMAN_REVIEW) is correct for the real policy just published — this is now testable with real, if minimal, production configuration, not blocked.

## Evidence generation and signing verification

**Check:** the intent above produces a signed Evidence record. Confirm its `key_id` matches the production signing key decided in Phase 2/4; confirm `GET /v1/evidence/verification-keys` returns a public key matching an independently-computed value from the installed private key (same method as Milestone 5).
**Pass criterion:** signature verifies; `key_id` is the production key, not a leftover placeholder or staging value.

## Blob uploads

**Check:** through the application's own document-upload endpoint (not the infrastructure-level RBAC test already done in Milestone 4), upload one real document as part of the smoke test.
**Pass criterion:** the document is retrievable through the application afterward, not just present in the storage account directly.

## Managed Identity

**Check:** confirm the prod Container App's identity holds exactly the same role shape already proven correct for staging (`Key Vault Secrets User`, `Storage Blob Data Contributor`, `AcrPull` — scoped to prod's own resources, not staging's).
**Pass criterion:** live `az role assignment list` matches this shape exactly.

## Key Vault

**Check:** unauthenticated secret access rejected (`401`), same test performed against staging in Milestone 3.
**Pass criterion:** `401`, confirming the identity-first RBAC model applies identically to the new prod vault.

## PostgreSQL

**Check:** Alembic at head; backup retention and PITR configured per `prod.tfvars`'s geo-redundant setting.
**Pass criterion:** `alembic current` matches the expected head revision; `az postgres flexible-server show`'s backup block shows the geo-redundant configuration actually took effect (a real difference from staging worth confirming, not assuming from the tfvars alone).

## Azure Monitor / Application Insights

**Check:** real telemetry flowing — container logs in Log Analytics, and (if `APPLICATIONINSIGHTS_CONNECTION_STRING` is wired for this environment, as it is for staging since Milestone 5) real `requests`/`dependencies`/`traces` data from the smoke test's own traffic.
**Pass criterion:** live query returns non-zero rows generated by the smoke test specifically, not stale data from an unrelated source.

## Alert rules

**Check:** all five rules present and `Enabled`, scoped to prod's own resource IDs (not accidentally left pointing at staging's).
**Pass criterion:** `az monitor metrics alert list --resource-group <prod-rg>` returns 5, matching `modules/alerts`'s design.

## Overall pass condition for this checklist

Every item above passes using **real production data created during this checklist's own smoke test** — the first real organization, the first real policy, the first real Evidence record. This is a materially stronger verification than the prior program could achieve with synthetic-only checks, precisely because there is no historical data to work around.
