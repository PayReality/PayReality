# Milestone 3: Security Review

## Why identity-based management was chosen over network isolation for Key Vault and Storage

Milestone 2's original design set `public_network_access_enabled = false` on both Key Vault and Storage, relying entirely on their Private Endpoints for access. That works for the running application (which lives inside the VNet) but not for Terraform itself: this project's Terraform runs from outside the VNet, and no VPN, bastion, or self-hosted runner exists to put it inside one. Discovered live, not in design review: every `terraform apply` against either resource failed outright once network isolation was enforced.

Building a jump host, bastion, VM, or self-hosted runner solely to give Terraform network-level access was **explicitly rejected** — it would be real, ongoing infrastructure (cost, patching, its own attack surface) whose only job is working around an identity model that already solves the same problem more simply. Azure RBAC plus Microsoft Entra ID authenticates every request to both resources regardless of network path; the public endpoint is not an open door, it is a door that checks identity instead of network location. This was the user's explicit direction, given after the alternative (keep the network block, add a jump host) was presented as a real trade-off, not decided unilaterally.

## What changed, concretely

- **Key Vault**: `public_network_access_enabled` → `true`, `network_acls.default_action` → `"Allow"`. `enable_rbac_authorization` stays `true` — **access policies were never enabled and remain rejected** as an authorization mechanism.
- **Storage**: `public_network_access_enabled` → `true`. `allow_nested_items_to_be_public` stays `false` — no container or blob can be made public regardless of network path.
- Both resources' **Private Endpoints are untouched** and remain the path the running application actually uses when inside the VNet.

## Every RBAC role assigned, and why

| Resource | Identity | Role | Scope of what it can do |
|---|---|---|---|
| Key Vault | Terraform-operator (signed-in user) | `Key Vault Secrets Officer` | Create/manage secret **values** only — not certificates, not keys, not the vault's own access model. The minimum built-in role that can do what Terraform needs; `Key Vault Administrator` was considered and rejected as broader than necessary. |
| Key Vault | Container App managed identity | `Key Vault Secrets User` | Read-only. Cannot create, rotate, or delete a secret — rotation stays a human/CI action. |
| Storage | Terraform-operator (signed-in user) | `Storage Blob Data Contributor` | Create/manage containers and blobs. |
| Storage | Container App managed identity | `Storage Blob Data Contributor` | Same role as the operator — the application legitimately needs read/write (uploads, evidence exports), so no narrower built-in role fits without also blocking a real, intended use. |
| Container Registry | CI/CD managed identity | `AcrPush` | Push images only — carried over unchanged from Milestone 2. |
| Container Registry | Container App managed identity | `AcrPull` | Pull only — carried over unchanged from Milestone 2. |

No identity holds a role it doesn't actively use. No shared credential, connection string, or access key exists anywhere in this design — every credential is either a managed identity token or a Key-Vault-resolved secret injected at the platform level, never in Terraform state as a plaintext variable.

## Resulting security model — verified live, not just configured

| Check | Method | Result |
|---|---|---|
| Key Vault rejects unauthenticated reads | `curl` the vault's REST API with no token | `401 Unauthorized` |
| Storage rejects anonymous container access | `curl` a container listing with no auth | `409` (blob public access disabled) |
| Postgres has no public network path at all | `az postgres flexible-server show` | `publicNetworkAccess: Disabled` |
| No plaintext secret in Terraform state/config | Manual review of `environments/*.tfvars` and every module | Confirmed — `DATABASE_URL` and the Postgres admin password are generated by Terraform and written directly to Key Vault, never round-tripped through a variable |
| TLS enforced everywhere | Storage `minimumTlsVersion=TLS1_2`, `enableHttpsTrafficOnly=true`; Postgres connection string carries `sslmode=require`; Container App ingress `allow_insecure_connections=false` | Confirmed |
| Least privilege | Full role-assignment audit (above table) | Every identity's role matches exactly what it does — no wildcard, no `Owner`/`Contributor` grants below the subscription level |
| Application secrets still placeholder | `EVIDENCE_SIGNING_KEY_B64` etc. hold `PENDING-MILESTONE-5-MANUAL-ENTRY` | By design — see `MILESTONE_3_KNOWN_ISSUES.md`; the app's own graceful-degradation path logs and continues rather than crashing |

## What this milestone did not change

Repository rules were respected throughout: no file under `server/`, `SPECIFICATION/`, or `PRODUCT_ROADMAP/` was touched. The application's own authorization logic, signing scheme, and OPA policies are exactly what they were before this migration — this review covers Azure's access controls around the application, not the application's own security logic (already covered by prior phases' work: the evidence signing key rotation fix and the RBAC/Organisation Settings work).
