# Part 45 — Phase 5 Broken Promise Report

**Status:** final. **Baseline:** [23](23_RUNTIME_GOVERNANCE_MIGRATION_BASELINE.md). **Method:** Phase 5's Objective 3 — every named architectural promise, classified HELD / PARTIALLY HELD / VIOLATED / UNKNOWN, with direct evidence. Objective 4 (Silent Architectural Risks) is folded into this report's final section, since a silent risk is, in every case found, a promise that is HELD today with no structural guarantee against it silently breaking tomorrow.

## Classification

| Promise | Verdict | Evidence |
|---|---|---|
| **Single writer** (to the active Policy row / OPA's `authorization` package) | **HELD** | `runtime_policy_service._is_unexpected_active_writer`, tested by 3 dedicated tests since Phase 2; confirmed exactly one live call site of `upload_policy` (`runtime_policy_service.py`); all four legacy write endpoints return HTTP 410, tested. |
| **Fail closed** | **HELD** | `domain/decision/engine.py::evaluate` — exactly one code path reaches `ALLOW` (`result.get("allow") is True and result.get("deny") is not True`); every exception type and every other response shape resolves to `HUMAN_REVIEW`. Tested by `test_decision_engine.py`, documented in [12_DECISION_ENGINE.md](12_DECISION_ENGINE.md) §12.1/§12.5. |
| **Append-only evidence** | **HELD** (see Silent Risks below for the caveat) | Direct search of `server/app` found zero call sites mutating or deleting an `Evidence` row anywhere — every reference is either `db.get` (read) or `db.add` (insert). |
| **Immutable decision** | **HELD** (see Silent Risks below for the caveat) | Same search method, zero hits mutating a `Decision` row; `DecisionResolution` exists as a *separate* table specifically so resolving a `HUMAN_REVIEW` decision never requires updating the original row (spec 8.2's own stated guarantee). |
| **Replayability** | **HELD**, materially strengthened this migration | [36_PHASE_4_CONTEXT_INTELLIGENCE_SPEC.md](36_PHASE_4_CONTEXT_INTELLIGENCE_SPEC.md)'s classification found and closed the one real gap (`principal_name`, Phase 4). Every other context element was already independently confirmed persisted and joinable. |
| **Policy determinism** | **VIOLATED — found and fixed this phase** | `runtime_policy_service.reconcile_opa_with_active_policies` and `_other_active_policies` both queried "every active RuntimePolicy" with no `ORDER BY`. Postgres does not guarantee row order without one; the same active-policy set could physically return in a different order across two compiles, and `build_bundle` serializes policies in whatever order it receives them, so `bundle_hash` could differ for zero actual policy change. Existing tests (`test_bundle_builder.py`) held the input list literally fixed and so could not have caught this — they tested `build_bundle`'s own determinism given a list, never the caller's guarantee that the list itself is stable. Fixed: both queries now carry `.order_by(RuntimePolicyRecord.policy_key)`. Two new tests (`test_policy_compilation_ordering.py`) assert the ordering clause is present on both statements, without requiring a real database. See [48_PHASE_5_IMPLEMENTATION_REPORT.md](48_PHASE_5_IMPLEMENTATION_REPORT.md). |
| **Dependency boundaries** | **PARTIALLY HELD** | The two most safety-critical edges — Runtime Authority's purity, `domain/`'s freedom from `app.db` — are continuously, automatically verified (Phase 2's AST tests, run on every `pytest` invocation). The general promise ("no forbidden edge exists anywhere in this codebase") is not comprehensively enforced by any tool; it holds today by direct inspection (this audit re-confirmed it), not by a check that would fail if a new, undeclared edge appeared somewhere Phase 2's two specific tests don't look. |
| **Runtime Authority separation** | **HELD** | `test_decision_engine_imports_nothing_from_db_services_or_routers`, unchanged since Phase 2, still passing. |
| **Runtime Truth separation** | **HELD — now continuously verified, previously true only by inspection** | Phase 2 tested Runtime Authority's independence *from* Runtime Truth's implementation; nothing tested the reverse (whether Runtime Truth could grow a dependency back onto the evaluation engine). Confirmed true by inspection before this phase; now covered by a new test (`test_runtime_truth_boundary.py::test_runtime_truth_service_never_imports_the_decision_engine`), completing the pair. |
| **Context persistence** | **HELD** | [36](36_PHASE_4_CONTEXT_INTELLIGENCE_SPEC.md)'s full classification table; every context element reaches either `Intent.context` (caller-supplied) or `Evidence.payload` (runtime-enriched), both write-once. |
| **Evidence completeness** | **HELD, for every field this architecture's own replay coordinate requires** | `authority_version`, `policy_version`, `policy_bundle_hash`, `authority_context`, `delegation_chain`, and (as of Phase 4) `principal_name` are all present on every real evaluation's Evidence record. `currency` is absent from the payload but present, immutable, and joinable via `Intent.currency` — the same "persisted elsewhere, not duplicated" pattern already established for the caller-supplied `context` dict, not a completeness gap. |

## Silent Architectural Risks (Objective 4)

Every promise above marked HELD is true today, verified directly against running code. None of the following are currently-manifesting violations — they are documented because Phase 5's mandate is to search for failures that are *possible but undocumented*, and each of these is possible, with evidence, even though none has happened.

- **Append-only evidence and immutable decision hold by absence of code, not by a structural guarantee.** No database-level constraint (no `REVOKE UPDATE`, no trigger, no application-level guard) prevents a future service function from calling `db.query(Evidence).update(...)` or the equivalent on `Decision`. Nothing in the test suite would fail if one did, until a human noticed. This is the same category of risk Phase 1–4 have repeatedly closed for *other* promises (single writer, dependency purity) by converting "true by convention" into "true by test" — this pair remains in the "by convention" state.
- **Dependency boundaries beyond the two AST-tested edges are unmonitored.** A new module anywhere in `domain/` or `services/` could introduce a genuinely forbidden coupling (not `app.db`, not the two edges Phase 2 tests) and nothing would fail — it would need to be caught by code review, the same way this migration's own reconnaissance initially got the legacy-compiler status wrong before checking directly ([23_RUNTIME_GOVERNANCE_MIGRATION_BASELINE.md](23_RUNTIME_GOVERNANCE_MIGRATION_BASELINE.md) §23.1).
- **Documentation staleness has already recurred twice with no mechanism to prevent a third instance.** `MASTER_ROADMAP.md` and `VERSION_3_ROADMAP.md` independently drifted out of sync with delivered work; `SECURITY.md` drifted in a safety-relevant way. Nothing detects this automatically — every instance found in this audit was found by a human/agent reading the document directly, once, this phase. The SPECIFICATION documents this very migration program has produced (this file included) carry the identical risk the moment a future code change isn't accompanied by a documentation update.
- **Duplicated ownership of forward-planning has already happened twice** (`MASTER_ROADMAP.md`, `VERSION_3_ROADMAP.md`) and nothing prevents a third roadmap document from being created without either being retired or cross-referenced.
- **Policy determinism's fix (this phase) closes the two known query sites; it does not close the general class.** Any future query against `RuntimePolicyRecord` (or an equivalent table) written without an explicit `ORDER BY` and then fed into something hash-sensitive would reproduce the same failure mode. No lint rule or test enforces "every query whose result feeds a hash must be ordered" as a general principle — only the two specific instances found this phase are now fixed.

## What this report does not claim

It does not claim these risks are likely, urgent, or that the two-query fix and the one new boundary test eliminate the underlying *category* of risk. They eliminate the two specific instances found. See [47_PHASE_5_NEED_ANALYSIS.md](47_PHASE_5_NEED_ANALYSIS.md) for whether building general-purpose infrastructure against the category is actually justified by this evidence.
