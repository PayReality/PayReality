# Part 36 — Phase 4: Context Intelligence Specification

**Status:** final. **Baseline:** [23](23_RUNTIME_GOVERNANCE_MIGRATION_BASELINE.md). **Grounded in:** `schemas/intent.py`, `services/intent_service.py`, `services/runtime_truth_service.py` ([30](30_PHASE_3_RUNTIME_TRUTH_SPEC.md)), `services/authority_context_service.py`, `db/models.py::Intent`/`Evidence`.

## Purpose

Context Intelligence classifies every piece of information that reaches a Decision by lifecycle property — immutable or ephemeral, persisted or not, replayable or not — and states plainly which of it can affect Runtime Authority, which affects Resolution, and which affects neither. This platform already enriches, evaluates against, and stores context. Nothing here is new; this document names what already happens.

## The two sources of context, and one asymmetry between them

Every Decision's `context` dict (built in `intent_service.submit_intent`, line: `{**context, "timestamp": ..., "authority": resolved.authority_context}`) has exactly two origins:

1. **Caller-supplied context** — `SubmitIntentRequest.context`, an open `dict[str, Any]` the Agent submits verbatim.
2. **Runtime-enriched context** — `resolved.authority_context`, produced by Runtime Truth ([30](30_PHASE_3_RUNTIME_TRUTH_SPEC.md)) immediately before evaluation, plus the `timestamp` key derived from `requested_at`.

## The one gap this phase closed

`acting_for_principal_id`'s resolved **name** — the literal string OPA matches against `scope.principal` — was computed by Runtime Truth and used for evaluation, but only `principal_id` (a stable FK, not the string actually evaluated) was carried into `Evidence.payload`. Every other value Runtime Authority evaluates against has, since Phase 1, been pinned explicitly onto the Decision/Evidence record it produced (`policy_version`, `policy_bundle_hash`, `authority_version`, the full `authority_context` dict) specifically so replay never has to trust a live, mutable row to mean what it meant at evaluation time. `principal_id` alone breaks that discipline: reconstructing "what name did this Decision actually match against" requires dereferencing `principal_id` through the *current* `principals` table, which nothing prevents from having changed since. See the Migration Report ([41](41_PHASE_4_MIGRATION_REPORT.md)) for the fix: `principal_name` is now an additive field on `Evidence.payload`, populated with the exact string `runtime_truth_service.resolve()` already produced — no new resolution logic, only a new place an existing value is written.

## What this specification deliberately does not do

- It does not change how or when context is resolved. Runtime Truth's resolution order, sources, and freshness ([29](29_PHASE_3_RESOLVER_INTELLIGENCE_SPEC.md)/[30](30_PHASE_3_RUNTIME_TRUTH_SPEC.md)) are unmodified.
- It does not duplicate the caller-supplied `context` dict onto `Evidence.payload`. `Intent.context` is write-once and permanently joinable via `decision_id -> intent_id`, exactly as strong a replay guarantee as anything stored directly on Evidence — duplicating it would add storage and a second source of truth for a value that already has exactly one, immutable, home.
- It does not attempt to make `Principal` rows structurally immutable (e.g., by removing write access at the DB level). That would be a runtime/data-model change this phase's mandate explicitly forbids ("do not redesign context handling"); pinning the resolved name onto Evidence achieves the actual goal (replay integrity) without touching Principal's mutability at all.
